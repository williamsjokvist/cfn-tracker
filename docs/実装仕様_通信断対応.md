# 実装仕様 — cfn-tracker 通信断対応

対象リポジトリ: このリポジトリ（williamsjokvist/cfn-tracker の fork）
対象ブランチ: `fix/resilient-tracking`（分岐元 `upstream/master` = `88326ce`）
発注元: `CFNT_L/docs/code-1.md`（暫定仕様）
根拠となる調査: `CFNT_L/docs/調査結果_cfn-tracker.md`（欠陥の所在を行番号で特定済み）

## 0. このタスクのゴール

**通信が切れてもアプリが黙って止まらないようにする。**

現状は、ネットワーク断でポーリングが1回失敗しただけで監視が終了し、しかも
**UI には「追跡中」と表示され続ける**（＝ユーザーは異常に気づけない）。
これを「自動で再試行して復旧する」「復旧できないなら理由を告げて止まる」
「再試行中であることが画面で分かる」の3点を満たす状態にする。

### 受入条件（code-1.md 6章 = 最終的な合否）

1. 対象サイトへの一時的アクセス失敗時に**自動復旧する**
2. SSE 切断時に**自動再接続する**（クライアント側は既に標準 EventSource で動作。サーバ側を直す）
3. **停止・再試行中の状態が UI 上で明示される**

## 2. 修正仕様 A — エラー分類（新規）

現状「一時的（再試行で直る）」と「恒久的（人間の介入が要る）」を区別する手段が無い。
これが無いとリトライの実装ができないため、**最初にこれを作る**。

### A-1. HTTP ステータスを保持するエラー型

新規ファイル `app/pkg/model/http_error.go`:

```go
type HTTPStatusError struct {
    Op         string // "fetch battle log" 等
    StatusCode int
}
func (e *HTTPStatusError) Error() string  // 例: "fetch battle log: http status 429"
```

**適用箇所（この2つだけ変更する）**

- `app/pkg/tracker/t8/wavu/client.go:90` — `resp.StatusCode != http.StatusOK` の分岐で
  `&model.HTTPStatusError{Op: ..., StatusCode: resp.StatusCode}` を返す
- `app/pkg/tracker/sf6/cfn/client.go:59` — `bl.Common.StatusCode != 200` の分岐で同様
  （Buckler は JSON ボディ内の `Common.StatusCode` が実質のステータス）

### A-2. パース失敗を判別できるエラー型

新規 `app/pkg/model/parse_error.go`:

```go
type ParseError struct {
    Op  string
    Err error
}
func (e *ParseError) Error() string
func (e *ParseError) Unwrap() error
```

**適用箇所**: `cfn/client.go:53`（JSON unmarshal）、`wavu/client.go:58`（JSON unmarshal）、
`wavu/client.go:94`（goquery）の3つ。既存の `fmt.Errorf("...: %w", err)` を `&model.ParseError{...}` に置換。

### A-3. 分類関数

新規 `app/pkg/model/classify.go`:

```go
type ErrorClass int
const (
    ClassTransient ErrorClass = iota // 再試行で回復しうる
    ClassAuth                        // 認証切れ。再認証が要る
    ClassParse                       // レスポンス構造の不一致
    ClassFatal                       // 人間の介入が要る
)
func ClassifyPollError(err error) ErrorClass
```

**判定規則（上から順に評価し、最初に一致したものを採る）**

| 条件 | 分類 |
|---|---|
| `errors.Is(err, context.Canceled)` | 呼び出し側で先に `ctx.Err()` を見て処理するため分類対象外 |
| `HTTPStatusError` かつ 401 / 403 | `ClassAuth` |
| `HTTPStatusError` かつ 404 | `ClassFatal` |
| `HTTPStatusError` かつ 429 または 5xx | `ClassTransient` |
| `HTTPStatusError` かつ その他 4xx | `ClassFatal` |
| `ParseError` | `ClassParse` |
| `net.Error` で `Timeout()` が true | `ClassTransient` |
| `errors.Is(err, context.DeadlineExceeded)` | `ClassTransient` |
| `*net.OpError` / `*net.DNSError` / `syscall.ECONNREFUSED` / `ECONNRESET` / `EHOSTUNREACH` | `ClassTransient` |
| **上記いずれにも該当しない** | **`ClassTransient`** |

> **最後の行が重要**: 分類できないエラーは `ClassTransient` に倒す。
> 「知らないエラーだから止める」は無言停止への逆戻りであり、本タスクの目的に反する。
> 誤って再試行し続ける方が、誤って黙って止まるより望ましい。

## 3. 修正仕様 B — ポーリングループ（`app/cmd/tracking.go`）

**本タスクの中核。** 以下の定数を `tracking.go` の先頭に定義する（マジックナンバー禁止）。

```go
const (
    pollInterval       = 30 * time.Second // 既存動作を変えない
    retryBaseDelay     = 2 * time.Second
    retryThrottleDelay = 5 * time.Second  // 429 の初期待機
    retryMaxDelay      = 60 * time.Second
    parseFailThreshold = 3                // 連続パース失敗で「構造変化の疑い」へ
    parseRetryDelay    = 5 * time.Minute  // 構造変化疑い時の低頻度再試行
    maxReauthAttempts  = 3                // 認証切れからの再認証の上限
)
```

### B-1. 必須の不変条件（violation は defect）

1. **`matchChan` は、ポーリング goroutine のどの離脱経路でも必ず閉じる。**
   `defer close(matchChan)` を goroutine の先頭に置くこと。
2. **チャネル送信は必ず `ctx.Done()` との `select` で行う。** 裸の `ch <- v` を残さない
   （対象: `tracking.go:124`, `:127`, `:137`, `:236`）。
3. **`StartTracking` は必ず有限時間で戻る。** 戻らない経路を作らない。
4. **監視が止まる時は、止まる理由を必ずイベントで通知してから止まる。**
   通知なしに終了する経路を1本も作らない。
5. **`Poll` のエラーを握り潰さない。** 必ず `slog` に出す（分類・試行回数を含める）。
6. **再試行に回数上限を設けない**（`ClassTransient` の場合）。上限は「黙って死ぬ経路」になる。
   認証再試行（`maxReauthAttempts`）とパース失敗（`parseFailThreshold`）だけは例外的に上限を持つ。

### B-2. リトライの挙動

- **バックオフ**: `min(retryMaxDelay, base * 2^(attempt-1))` に**完全ジッター**を掛ける
  （`rand.Int63n(計算値)`）。`base` は通常 `retryBaseDelay`、429 のときだけ `retryThrottleDelay`。
- **再試行は待機後ただちに再ポーリングする。** 次の 30 秒ティックを待たない。
- **成功したら試行回数を 0 に戻し**、直前に失敗していた場合のみ復旧を通知する。

### B-3. 分類ごとの動作

| 分類 | 動作 |
|---|---|
| `ClassTransient` | 上限なしでバックオフ再試行。毎回 `tracking-retrying` を発火 |
| `ClassAuth` | `gameTracker.Authenticate` で再認証を試みる。成功ならポーリング継続。<br>`maxReauthAttempts` 回失敗したら `ClassFatal` と同じ扱い |
| `ClassParse` | 連続 `parseFailThreshold` 回までは `ClassTransient` と同じ。<br>超えたら「構造変化の疑い」として `parseRetryDelay` 間隔の低頻度再試行に切替え、<br>`tracking-retrying` の `reason` にその旨を入れる。**ここでも終了はしない** |
| `ClassFatal` | `tracking-error` を発火してからループを終了する |

### B-4. 発火するイベント（新規3種）

`EventEmitFn` 経由。フロントエンドはこれを購読する。

```go
// tracking-retrying — 再試行に入るたび
type RetryStatus struct {
    Attempt       int    `json:"attempt"`       // 連続失敗回数（1始まり）
    NextRetryInMs int64  `json:"nextRetryInMs"` // 次の試行までのミリ秒
    Reason        string `json:"reason"`        // i18n キー: "errNetwork" / "errThrottled" / "errStructureChanged" / "errAuth"
}

// tracking-recovered — 失敗が続いた後に成功したとき（データ不要）

// tracking-error — 続行不能で終了するとき
// ペイロードは既存の model.FormatError(err) と同じ形（localizationKey を持つ）
```

既存の `match` / `stopped-tracking` / `auth-progress` は**名前も形も変えない**（後方互換）。
`stopped-tracking` は従来どおり `StartTracking` の `defer` で必ず発火させる。

### B-5. その他の修正

- **1-2b**: DB 保存失敗時は `break` して `return nil` するのをやめ、`tracking-error` を発火し
  `cancel()` してから**エラーを返す**。
- **1-2c**: `ForcePoll` は `ctx.Done()` と `default` を伴う非投機的な送信にし、
  ポーリングが動いていないときは**即座に戻る**（ブロックしない）。
  `forcePollChan` の生成・クローズ・nil 代入は `sync.Mutex` で保護する。

### B-6. テスト可能性の確保（必須）

現状 `gameTracker` は非公開で `SelectGame` からしか設定できず、
外部テストパッケージ `cmd_test` からポーリングループを試験できない。
既存の `SetEventEmitter` と同じ形で**公開セッターを追加**する:

```go

```

## 4. 修正仕様 C — SSE サーバ（`app/pkg/server/server.go`）

受入条件2に対応。**クライアント側（`static/index.html`）は変更しない**
— 標準 `EventSource` の自動再接続が既に有効に動いているため（調査結果 2-3）。

1. `handleStream` の第2引数を `req *http.Request` として受け取り、`req.Context()` を監視する。
2. `sseChans []chan []byte` を **`map[chan []byte]struct{}`** に変え、
   `sync.Mutex` で保護する。登録は接続時、**削除は `defer` で確実に行う**。
3. 配信ループ（`:43-47`）は**ノンブロッキング送信**にする
   （`select { case ch <- data: default: }`）。読み取りの遅いクライアント1つが全体を止めない。
4. `req.Context().Done()` で `for` を抜け、handler を確実に戻す。
5. **15 秒間隔で heartbeat コメント行 `: keep-alive\n\n` を送出**する。
   これにより中間プロキシのアイドル切断を防ぎ、切断も早期に検知できる。
6. `fmt.Fprintf` の戻り値を検査し、書き込みエラーが出たら接続を終了する。
7. 既存の「接続時に `lastMatch` を再送する」挙動（`:77-81`）は**維持する**
   （再接続時の取りこぼし対策として機能しているため）。`lastMatch` へのアクセスも Mutex で保護する。

## 7. 検証コマンド（Codex 側で必ず全て通すこと）

作業ディレクトリは `app/`（`go.mod` のある場所）。

```bash
export GOMODCACHE=/tmp/gomodcache
export GOCACHE=/tmp/gocache
cd app
gofmt -l ./cmd ./pkg              # 出力が空であること
go build ./cmd/... ./pkg/...
go vet   ./cmd/... ./pkg/...
go test  ./cmd/... ./pkg/... -count=1
```

> **`./...` を使ってはいけない。** リポジトリ root の `main` パッケージ（`app/main.go`）だけが
> Wails を import しており、Wails は Linux 上で GTK / WebKit2GTK の開発ヘッダを要求する。
> 実行環境の WSL にはそれらが無い（`pkg-config` すら無い）ため、`./...` は
> **実装の良し悪しと無関係に必ず失敗する**。
> `main.go` は変更対象外なので、`./cmd/...` と `./pkg/...` だけを対象にすれば十分。
> root パッケージのビルド確認は Windows 側で別途行う。

`go test -race` は WSL 側に C コンパイラが無いため**実行しなくてよい**（Windows 側で別途行う）。
フロントエンド（TypeScript）のビルド・型検査も Windows 側で行うため、**実行しなくてよい**。
ただし `tracking-machine.ts` 等の変更は、型が通る形で書くこと。

### やってはいけないこと

- **`wails build` / `bun install` / `npm install` を実行しない。**
  フロントエンドのビルドは Windows 側で行う。WSL 側には bun も WebView2 も無い。
- **`upstream/master` に対して不要な差分を作らない。** リファクタリングは行わず、
  本仕様に書かれた欠陥の修正だけを行う。
- **新規の外部依存を追加しない。** 標準ライブラリと既存の依存だけで実装する。
- 改行コードは **LF 固定**。
