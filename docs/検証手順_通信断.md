# 実機検証手順 — 通信断対応

対象: `fix/resilient-tracking` ブランチのビルド成果物
比較対象: `build-baseline/CFN Tracker (baseline 88326ce).exe`（修正前・上流そのまま）

---

## 0. 前提: 認証情報の供給

SF6 のトラッキングには Capcom ID（CapID）のログインが要る。
**認証情報はバイナリに焼き込まない。** `.env` ファイルを exe と同じディレクトリに置く方式を使う
（`app/main.go:95-107` — `.env` があれば環境変数から読み、無ければ ldflags 埋め込み値にフォールバックする）。

`app/build/bin/.env` を以下の内容で作成する（**このファイルは `.gitignore` 済み**）:

```
CAP_ID_EMAIL=<あなたのCapcom IDのメールアドレス>
CAP_ID_PASSWORD=<パスワード>
HEADLESS=true
BROWSER_SOURCE_PORT=4242
```

> ログイン処理を目視したい場合は `HEADLESS=false` にするとブラウザ画面が出る。
> 初回やログイン失敗の切り分けに有効。
>
> **この `.env` はリポジトリにコミットしないこと。** `.gitignore` に登録済みだが、
> `git status` に出ていないことを毎回確認する習慣を持つのが安全。

### `.env` は必須（省略できない）

認証情報のフォールバック先である `main.capIDEmail` / `main.capIDPassword` は
ldflags で埋め込む変数で、**既定値が空文字**（`app/main.go:47-48`）。
本検証用ビルドでは意図的に埋め込んでいないため、**`.env` が無いと SF6 のログインは必ず失敗する。**

逆に `.env` は存在するのにキー名が足りない場合は、`envconfig` の `required:"true"` により
**起動直後に `log.Fatalf` で落ちる**（ウィンドウが一瞬も出ない）。
起動しないときは、まず `.env` のキー名の綴りを疑う。

## 1. 起動

**カレントディレクトリが exe と同じ場所である必要がある。**
`.env` もログファイルも**相対パスで解決される**（`godotenv.Load(".env")` /
`os.OpenFile("cfn-tracker.log", ...)`）ため、別の場所から起動すると `.env` が読まれない。

```powershell
cd C:\dev\cfn-tracker\app\build\bin
.\"CFN Tracker.exe"
```

エクスプローラからダブルクリックする場合はカレントディレクトリが exe の場所になるので問題ない。

ログは同じディレクトリの `cfn-tracker.log` に出る。
このファイルは **ビルド時に `-ldflags "-X main.isProduction=true"` を渡した場合のみ**生成される
（本検証用ビルドでは指定済み）。素の `wails build` で作り直すとログは stderr に出るようになり、
このファイルは作られないので注意。

検証中は別ウィンドウで追尾しておくと原因切り分けが早い:

```powershell
Get-Content C:\dev\cfn-tracker\app\build\bin\cfn-tracker.log -Wait -Tail 20
```

## 2. 通信断の作り方（★重要）

**NIC を無効化する方法は使わない。** RDP / Tailscale 経由で作業している場合、
自分の接続ごと切れて検証どころではなくなる。

代わりに **アプリ単体の送信をファイアウォールで止める**。狙いが正確で、
他の作業への巻き添えが無く、復旧も一瞬で済む。

```powershell
# --- 通信を切る（管理者権限が要る） ---
New-NetFirewallRule -DisplayName "BLOCK cfn-tracker (test)" `
  -Direction Outbound -Action Block `
  -Program "C:\dev\cfn-tracker\app\build\bin\CFN Tracker.exe"

# --- 通信を戻す ---
Remove-NetFirewallRule -DisplayName "BLOCK cfn-tracker (test)"
```

> 検証が終わったら**必ず規則を削除する**こと。残すとアプリが恒久的に通信できなくなる。
> 消し忘れを疑ったら `Get-NetFirewallRule -DisplayName "BLOCK cfn-tracker (test)"` で確認する。

## 3. 検証項目

`R2` `R3` `R5` が code-1.md 6章の受入条件に直接対応する。
**他が通ってもこの3つが落ちたら未完了。**

### R1 — 正常系（土台の確認）

1. `.env` を置いて起動し、SF6 を選択してログインが完了すること
2. CFN 名を入力して追跡を開始し、`追跡中` が表示されること

これが通らないと以降の検証ができない。落ちた場合は認証情報か `HEADLESS=false` で切り分ける。

### R2 — 通信断で「再試行中」が表示される ★受入条件3

1. R1 の状態でファイアウォール規則を追加して通信を切る
2. 最大30秒（ポーリング周期）待つ
3. **期待**: 画面に `再試行中（N回目・次回 M秒後）` が表示され、秒数がカウントダウンする
4. **期待**: 試行回数 N が増えていき、待機時間が 2s → 4s → 8s … と伸びて 60s で頭打ちになる
5. **期待**: `cfn-tracker.log` にポーリング失敗が分類つきで記録される

**修正前（baseline exe）との差**: baseline では画面が `追跡中` のまま何も起きず、
ログにも何も出ない。**この差が出ることが本検証の主眼。**

### R3 — 通信復帰で自動的に追跡が再開する ★受入条件1

1. R2 の状態でファイアウォール規則を削除する
2. **期待**: 次の再試行で成功し、`接続が回復しました` が出たうえで `追跡中` に戻る
3. **期待**: アプリの再起動も、追跡の開始し直しも要らない

### R4 — 長時間の断でも終了しない

1. 通信を切ったまま **30分以上**放置する
2. **期待**: 再試行を続けており、アプリは終了していない（再試行回数に上限は無い）
3. **期待**: 通信を戻せば R3 と同じく復旧する

### R5 — SSE オーバーレイの自動再接続 ★受入条件2

1. アプリ起動中にブラウザで `http://localhost:4242/` を開く（OBS のブラウザソースと同じもの）
2. 試合データが表示されることを確認
3. アプリを再起動する（＝サーバを落として上げる）
4. **期待**: ブラウザ側は再読込せずに自動で再接続し、表示が復活する
   （標準 `EventSource` の自動再接続。修正前からクライアント側は動作していた）
5. **期待**: ブラウザのタブを何度も開閉しても、アプリ側の goroutine が増え続けない

> 5 の確認方法: 検証中に `cfn-tracker.log` を見て、切断のたびに登録解除が記録されること。
> 修正前は登録されっぱなしでリークしていた。

### R6 — 認証切れ（任意・時間がかかる）

1. 長時間放置して CapID セッションを期限切れにする
2. **期待**: 自動で再認証を試み、成功すれば追跡が続く
3. **期待**: 再認証に3回失敗したら、**理由を表示したうえで**停止する（黙って止まらない）

## 4. 修正前との比較（推奨）

最も説得力のある確認は、同じ手順を2つの exe で実行して差を見ること。

| | baseline（`build-baseline/`） | 修正後（`app/build/bin/`） |
|---|---|---|
| 通信断のとき | `追跡中` のまま永久に固まる | `再試行中（N回目…）` |
| 通信復帰のとき | 何も起きない（要アプリ再起動） | 自動で `追跡中` に戻る |
| ログ | ポーリング失敗が**残らない** | 分類・試行回数つきで残る |

> baseline を動かすときも `.env` が要る。同じ `.env` を
> `build-baseline/` にコピーして使う。
